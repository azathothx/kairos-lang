# ADR-5x（1.1 RC 草稿）: 時点どうしの順序比較と標準糖衣 since／before——点集合を日時で切り出す

**判断**: 値層の順序比較 `<` `<=` `>` `>=` の定義域を「数値どうし」から「数値どうし・**時点どうし**」へ広げ、stdlib（Gregorian 公開語・`at` の隣）に糖衣 2 語を置く。

```
since(p)  = s => s |> filter(t => t >= p)     # p 以後（含む）  = s ∩ [p, ∞)
before(p) = s => s |> filter(t => t <  p)     # p より前（含まず）= s ∩ (−∞, p)
```

（発端＝90-open 3-8・需要 2 例〈11 §(n)・ブログ第 35 弾〉。受け皿 `epochOrdinal` 形は書けるが読みづらく、単位の問いを生んでいた）。

1. **1.0 は不変＝追加拡張**。1.0 で合法だった式の意味は一つも変わらない。時点どうしの順序比較は 1.0 では評価エラー（「数値ではない: point」）で、本 ADR はその形を**定義する**だけ（静的エラーだった形の合法化＝追加拡張。先例 ADR-45／RC5 追補 7・ADR-48）。文法・字句・既存の語は不変。糖衣は展開で消える（ADR-23／§4.8）。
2. **順序は chronos 上の瞬間の全順序**。等値 `==` の時点規則（§4.9）と同じ台。tz・暦法・粒度に依らない（リテラルは在圏 tz で時点に解決＝ADR-33）。**単位は持たない**——単位の問いは `epochOrdinal` の床比較に由来する人工物。補題: 目盛り上のリテラル p では `epochOrdinal(u,t) >= epochOrdinal(u,p) ⟺ t >= p`（現行正準と外延同値）。食い違うのは目盛り外（`14:30`＝床形は 14:00 を含む・瞬間形は 15:00 から）だけ。
3. **型違いはエラー**。時点と数値・ラベル・単独時刻 `Thh:mm`・ストリームは順序比較できない——1.0 追補 22 の等値エラーと同じ型名で診断し、単独時刻は ADR-51 の誘導へ。単独時刻どうしの順序は定義しない（3-11 と同時に判断）。
4. **境界は半開 [since, before)**＝評価範囲 `[from, to)`・`isOpen`・窓と同じ規約。`since(2026-10-26)` は在圏 tz の市民日の開始瞬間。日粒度の列に時刻付きリテラルを渡すと日の点は 00:00 なので `everyDay |> before(2026-11-04T17:00)` は 11-04 を**含む**——当日の扱いは日付を 1 日ずらす（評価範囲と同じ作法）。
5. **展開は filter に固定**。糖衣は展開先の意味を継承する（ADR-51 判断 5）——整列・窓を保存（`within(month) |> since(p) |> first` が成立）、輸送行は filter 行（新しい範囲外を生まない）、整列「なし」の和にも掛かる。`stride(1, from: p)` 展開は採らない（註釈が評価域の末尾まで膨張・終点の双対が無い）。
6. **ADR-34 判断 4（点±幅算術を導入しない）は不変**。順序は算術ではない——新しい点を作らず隣接窓参照の抜け道にならず、幅規約も tz 依存算術も値層へ入らない。ADR-34 へ改訂節で相互参照。
7. **名は `since`／`before`**（英語の含意が境界と一致・named-arg キー・core 語・公開語と綴りが重ならない）。**「今」は式に埋めない**——日単位の切り出しは評価範囲の分離が第一・時刻の切り出しだけ since／before・日時は引数や呼ぶ側で注入（ADR-52 判断 2 と同じ据え方）。

**背景**（1.0.10 の実走）: `t >= 2026-10-26T14:00` はエラー・`t == …` は通る・`epochOrdinal` 形は 51 点・利用側糖衣 `stride(1, from:)` も 51 点。差 `\` で作る before は整列「なし」の和で ADR-36 の静的エラー、窓付き入力では窓を落とし後段 `last` が I4 エラー。stride 形は註釈が 09-25..10-05 へ膨張（filter 形は ..10-01・点は同一）。終点の双対は 1.0 核だけでは書けない——核の順序比較が唯一の言語側の判断点。

**却下した案**:

- **`epochOrdinal` 単位形**（`since(hour, p)` 級）: 単位が情報を持たず目盛り外で床の罠。瞬間グリッドは `chronos grid 1s` が OOM。
- **`stride(1, from: p)` 展開**: 註釈の膨張・双対なし。受理拡大を認めない場合の since 限定の退路として記録。
- **差 `\`／`coincides` で作る before**: 整列なしで割れる・窓を落とす・無名テーブルの被覆行が出る。
- **名 `until`**（`takeLast` の点包含と同語で境界が反転）・**`from`／`to`**（named-arg と 2 役・"to" は包含に読まれる）・**`after`**（厳密に後）・**`between`**（SQL の両端包含・片側が書けない）。
- **core 語 2 つとして追加**: 核の最小集合（ADR-23）を増やし輸送表・整列表の行が要る。糖衣で足りる。

**帰結**:

- spec: §3.5 比較の行・§4.9「等値・順序の型」・§4.8 標準糖衣例・§5.4 命名・glossary §6.5。EBNF・輸送表・整列表は不変。
- impl: `evalBin` 4 case（数値／時点の分岐＋診断）・`gregorian.kairos` 2 行・witness・Playground 再構築・mcp 同梱 reference。
- 文書: reference/since.md・before.md 日英・stdlib 日英・epochOrdinal／takeLast／stride の落とし穴・11 §(n)・90-open 3-8 → 91。
- 版: 言語が変わるので **1.1.0**。CHANGELOG の節名と 4 入口の状態行の書式を先に決める。

**検証の案**: (a) 第 35 弾の `epochOrdinal` 形と糖衣形の 51 点が toEqual（変異＝境界反転で赤） (b) `before` の `<` を `<=` に変異→17:00 が出て赤 (c) 14:30 錨で 50 点・先頭 15:00（変異＝床比較で 51 点） (d) eval 09-25..10-05 で註釈がちょうど ..10-01（変異＝stride 展開で ..10-05） (e) 整列「なし」の和に `before` が掛かる（変異＝`\` 展開で ADR-36 エラー） (f) `within(month) |> since(p) |> first`＝[10-15, 11-01] (g) `t >= 5`・`since(T14:00)`・`weekday(d) >= Mon` が誘導つきエラー (h) 既存の数値比較 doctest が全数緑。
## 決める論点（審査役の一覧・推奨つき）と実装の順序

- 【1・中心】値層の順序比較 `< <= > >=` を時点どうしにも定義する受理拡大を 1.1 の「追加拡張」と認めるか。選択肢: (a) 認める——1.0 で合法だった式の意味は不変・評価エラーだった形の合法化（先例 ADR-45＝CHANGELOG.md:207「静的エラーだった形の合法化＝追加拡張」・ADR-48）。(b) 認めない——since だけを `stride(1, from: p)` 展開で入れ、before は見送り（1.0 核に終点の双対が無い＝実走 R5／R7b で差展開は整列なしと窓付きで割れる）。(c) since／before を糖衣でなく core 語 2 つとして足す（新語＝字義どおりの追加拡張だが、核の最小集合〈ADR-23〉を増やし輸送表・整列表の行が要る）。推奨: (a)。90-open 冒頭の定義「既存の式の意味は不変」を満たし、`==` が時点に定義済み（§4.9:380）なので順序への完成として説明が立つ。

- 【2】名。選択肢: (a) since／before——境界と英語の含意が一致・named-arg キー・core 語・公開語と重ならない（正本ツリーの .kairos／.md で 0 件）。(b) from／before——`from:` と同義（≥）で学習が転移・CLI `--from` と同じ向きだが、`from(` と `from:` の 2 役・`stride(3, from: x) |> from(y)` の字面。(c) since／until——英語の定型対だが `takeLast(n, until:)` の点包含（ADR-52 判断 6・glossary §6.5:135）と同語で境界が反転＝不採を勧める。推奨: (a)。意味論・実装は名に依存しない（stdlib 2 行の綴りだけ）ので、この決定は最後でよい。

- 【3】糖衣 2 語を受理拡大と同時に出すか、受理拡大だけ先行して様子を見るか。推奨: 同時。需要 2 例の動機は読みやすさ（`filter(t => isOpen(t) and t >= p and t < q)` ではラムダが残る）。受理拡大だけ先行は語彙を増やさない最小解として成立するので、凍結を最優先するならこちら。

- 【4】置き場と「影」。選択肢: (a) Gregorian 公開語（`at` と同じ・gregorian.kairos:30 の隣・新機構なし）。(b) 暦法非依存の言語水準の既定糖衣（新機構）。付随: lookupBinding（eval.ts:2091-2104）は premise → calendar-system → top の順なので、利用側 top-level の `since`／`before` 束縛は stdlib に黙って覆われる（`at` と同じ既存挙動）。手当て: (i) reference の落とし穴と Release 本文に明記（最小）。(ii) 「stdlib 公開語の top-level 再定義は静的エラー」の新規則（`at`・`monthStart` 等にも遡る＝1.0 で動いていたファイルが止まり得る）。推奨: (a)＋(i)。供給側コーパスの掃引を 1 回挟む（正本ツリーは 0 件）。

- 【5】日粒度の列に時刻付きリテラルを渡したときの扱い（`everyDay |> before(2026-11-04T17:00)` は 11-04 を含む＝実走 R10）。選択肢: (a) 文書化のみ（日の点は 00:00・当日の扱いは日付を 1 日ずらす＝評価範囲と同じ作法）。(b) 入力の粒度より細かいリテラルに警告。推奨: (a)。警告は粒度の静的知識を要し、整列「なし」の入力で判定できない。

- 【6】単独時刻どうしの順序（`T09:00 < T17:00`）を定義するか。推奨: 定義しない——chronos 上の位置を持たず（ADR-51 判断 2）、点から時刻を取る射影（3-11）が無いので実用が立たない。3-11 と同時に判断。

- 【7】1.1 の記録の書式。CHANGELOG の見出しは doc-consistency.test.ts:228 の正規表現 `^## (?:RC\d+|1\.0) 追補 (\d+)` が前提で、spec/README.md:6・README.ja.md:32・README.md・en/spec/README.md の状態行も「1.0（追補 N まで反映）」の形。選択肢: (a) 「## 1.1（日付）——…」の節を新設し、状態行を「1.1（…）」へ・正規表現を 1.1 対応に広げる。(b) 「1.1 追補 1」から通し番号を続ける。推奨: (a) を 1.1 RC 枝で先に決めて検査を直す（最初の変更で一斉に赤になる面）。版は impl 1.1.0・mcp・server.json・winget・exe。

- 【8】1.0 文書への先行案内。選択肢: (a) 1.1 まで待つ（Playground・MCP・検定の追従が 1 回で済む）。(b) 90-open 3-8・11 §(n) に「利用側糖衣 2 行（stride 形 since）」を今案内する。推奨: (a)。stride 形は註釈が膨張し before が無いので、教えると 1.1 で書き換えが要る。
