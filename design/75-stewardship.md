# 維持と継承の方針（2026-10-18）

Kairos がどう維持され、作者が関われなくなっても何が残るかを書く。利用者が安心して採用するための約束でもある。

## 柱 1: 言語は無料の標準

- 仕様・参照実装・Playground・文書は Apache-2.0。課金しない。
- 仕様は 1.0（2026-09-14）で凍結。追補は言語を変えない（CLI の出力形・配布の形・文書だけ）。
- 参照実装は実行時依存ゼロ。配布は npm・GitHub Release・Windows 単体 exe。

## 柱 2: 収益は言語の一つ上の層

言語そのものから収益は得ない。得るのは、言語を部品として使う層。

- 供給側のサービス: 祝日表の更新・premise の供給・発報（[発報層プロファイル](../spec/60-firing-layer-profile.md)）・購読。
- 導入支援: 複雑な規則を Kairos で書いて検証する仕事。
- 検定: 認定と教本。利用者が増えてから。

線引きは最初から決めてある。年で腐るデータを言語は配らない。状態を持つものは言語の外に置く。
この境目が、無料の層と有料の層の境目でもある。言語の維持費は上の層が払う。
多くの言語がこの型で維持されている（使う側の製品が言語を養う）。

## 柱 3: 維持費を低く保つ

- 凍結した仕様・依存ゼロ・800 本超の witness・公開は CI から（来歴つき）。
- 定期作業は 2 つだけ。年 1 回の祝日表の更新（例の資産）と、ドメインの更新。
- 何もしなくても残るもの: 公開リポジトリ・GitHub Pages・npm の公開済みの版・Release の資産。
- 小さな DSL の生存条件は収益ではない。維持費がほぼゼロであることと、必要とする人がいること。cron や iCalendar（RFC 5545）がその型。

## 柱 4: 継承は「凍結を守る管理者」へ

後継者に言語の設計は求めない。求めるのは次の 3 つ。

1. 公開物を消さない。ドメインを更新する。
2. 年 1 回、祝日表を延ばす（手順は [保守の手引き](../MAINTENANCE.md)）。
3. 仕様を変えない。変える必要が出たら、そのとき必要とする人が判断する。

備え:

- 識別子に個人名を含めない。winget は `KairosLang.Kairos`、npm は無スコープの `kairos-lang`。
- 持ち主を 2 人以上にする。リポジトリの owner・npm の maintainer・ドメインの連絡先。
- 中立の組織（コンソーシアム）へ移管する選択肢を残す。移管で変わらないもの: ライセンス・仕様・公開済みの版・URL（転送される）。

## 利用者への約束

- 公開済みの版は消えない。
- 仕様は凍結。追補は言語を変えない。
- fork は自由（Apache-2.0）。
- 受け付けを止める（保守モード）ときは README に明示する。
