# 公開文書の機械監査（2026-11-05・Batch API）——日英ミラーの意味の食い違いと、ja 文書の読みやすさ

公開文書を 2 つの物差しで機械的に読ませた。(a) 日英ミラーの**意味の食い違い**（日本語が正）、(b) 公開 ja 文書の**読みやすさ**（2026-10-10 の方針＝短文・柱・箇条書き・表は一覧だけ・詳細は別ファイル）。
`source_sha` の検査は鮮度（原文が変わったのに訳が追従していない）しか見ないので、意味の食い違いを機械で見たのは初めて。読みやすさも、段落長の機械検査（`paralen`）より一段深い「文の構造」の指摘が目的。

- 器: `tools/audit/batch-audit.mjs`（非公開の道具層）。Batch API に 1 文書 1 要求で投入し、構造化出力（所見の配列＝重さ・種類・引用・直し方）で受ける。
- モデル: 意味監査は Opus 5.5 と Sonnet 5.5 の 2 本（同じ箇所を両方が挙げたものに印）。読みやすさは Opus 5.5。effort high・adaptive thinking。

- 費用: 約 $7.9（Batch は半額。Opus 170 件 $6.7・Sonnet 90 件 $1.2）。
- 所見の全文（引用と直し方つき）は非公開の `tools/audit/results/2026-11-05/`（`fidelity.md`・`readability.md`・生の `results.jsonl`）。

## 2. 公開 ja 文書の読みやすさ

Opus 5.5 で 80 本に所見 941 件（high 197・medium 538・low 206）。同日に Sonnet 5.5 でも同じ 80 本を読ませた（924 件＝high 192・medium 515・low 217・約 $1.9）。両モデルが同じ箇所を挙げた所見は **350 件（うち high を含む 131）**＝処置はこの一致分から（統合表は `readability-merged.md`）。1 本あたりの上限 12 件に達した文書が多く、件数より中身を見る。high の種類の内訳＝読者が迷う 77・1 文が長い 48・初出の術語 32・結論が後ろ 16・構成 14・用語の揺れ 9。

読んで確かめた範囲では、指摘は的を射ている。例:

- `recipes/logistics-delivery.md`: 「15 時までの受注は当日出荷」と「ちょうどは翌営業日」と「受注時刻以上の最初の締め」が食い違って読める（事実の確認が要る）。
- `recipes/4-4-5-calendar.md`: 変種（4-5-4・5-4-4）の作り方が `mod 13` の値だけで、週番号の上限の変更が漏れている。P12 が吸収する週の数え方が表と合わない。
- `recipes/*.md` の 3 本: 「下のブロックの `@JP` は doctest の標準前提」の注記が、`@JP` を使わないブロックに付いている。
- `reference/split.md`・`reference/nth.md`・`spec/30-body-layer.md`・`spec/50-glossary.md`: 1 項目に定義・検査・例外・経緯が入れ子の括弧で詰まり、結論が取れない。
- `README.ja.md`: 「`impl/examples/` はこのリポジトリにある」の注記が、npm だけを入れた読者が最初のコマンドで止まる位置より後ろにある。

処置はこの記録では行わない。ja を直すと英語ミラーの追従（`source_sha`）が文書ごとに要るので、別の回に**文書単位**で進める。順の案＝(1) 事実の食い違いの候補（logistics・4-4-5・recipes の注記・bench README の P-10 の文）を実物と照合して直す (2) 入口（README.ja・spec/README・impl/README）(3) reference の長い項（split・nth・takeLast・roll・cycle・segmentBy・since）(4) spec 本文（30・50）。

## 5. 追加: ブログ記事の陳腐化監査（同日・Opus 5.5・32 記事・約 $2）

公開済み・予約済みの記事を、1.1.0（公開）と 1.1.1（準備中）の変更履歴に照らして読ませ、「今は違う・古い」記述を拾った（全文は非公開の `tools/audit/results/2026-11-05-audit2/blog.md`）。32 記事中 10 記事が differs（high 3・medium 14・low 25）。

- **1.1.1 で壊れる例**: 第 16 弾（前提の派生）の `premise Rota = Gregorian with {…}`・`premise R445 = ISOWeek with {…}` は `tz:` を宣言していない。1.1.1 の参照実装では日付リテラルの錨や市民日グリッドの評価が「tz: が未宣言」の静的エラーになり、記事の点列は出ない。**1.1.1 の公開前に記事を直す**（`with` の束に `tz:` を足すか軽量形の後置）。前文を省いた断片（第 13・14・24・31 弾ほか）は例示なので文脈で読めるが、「そのまま貼って動く」とは言わない。
- **1.1.1 で正しくなる例**: 第 18 弾（黙りの既定）「`tz:` の宣言がなければ静的エラー」と第 7 弾（日英）「宣言を必須」は、1.1.0 までの参照実装では成り立っていなかった（実行既定 tz に落ちていた）。1.1.1 で仕様どおりになる。版を添える 1 文で足りる。
- **時点の記述**: 「現在 RC・1.0 準備中」（第 1・5・6 弾）・「参照実装はプロトタイプ」「テスト 638 本・ADR 53 本・外部レビュー 12 回」（第 21 弾）・「以降 `kairos` は 1.0.1」（第 25 弾）・定型の「Kairos は設計中のスケジュール定義言語です」（第 11〜20 弾の約 8 本）。記事の時点としては正しいので、遡って直すかは運用の判断（10/22 の 492 のように `--update` で定型フッタだけ揃える手はある）。
